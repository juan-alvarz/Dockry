# Dockry review, November 2026

Written after the user found three bugs in a row on 2026-11-02 (a sound badge on the
wrong profile, Zen opened from Raycast switching profiles, the second screen showing
another profile's wallpaper), two of them made worse by first fixes that didn't hold.
It collects every issue raised in the project's sessions, says why fixes keep breaking
other things, and sets out the order to fix the structure in.

Companion files: `architecture.md` (the map), `findings.md` (the first read, items
1–20). The change that came out of it is `openspec/changes/profile-workspaces/`.

## Later the same day: two directions, one kept

1. **macOS desktops per profile (dropped).** The user asked for profiles that don't know
   about each other, and each profile became a macOS desktop (Space). It worked only
   after creating desktops in Mission Control, turning on "Switch to Desktop" shortcuts,
   turning off two Desktop & Dock options and moving windows by hand. Dockry can't create
   desktops itself (no public API; a Mission Control button press through Accessibility
   was tried), and every switch slides. The user found it awful; it was deleted unmerged.
2. **Workspaces of Dockry's own (kept).** As AeroSpace does: every window stays on one
   macOS desktop, other profiles' windows are parked off screen. What made the earlier
   parking buggy was everything around it, so this time: one mode, one record per window
   (`ProfileWindowRecords`), one rule for an app coming forward however it came
   (`ProfileAppRules.activated`, no launcher detection, no event-order guesses), no hidden
   apps, wallpapers without memory.

The user also stopped running Dockry during development ("figure out a way to do test
without my PC"): rules are tested in DockryCore, and the Mac-only checks are listed in the
change's `tasks.md` for the user.

## Why fixes break other things

Read from the history, not guessed. Each cause names where it showed.

1. **The rules lived in untested glue.** What a dock click does, what an app coming
   forward does, which profile an app is in, and which picture a screen shows were
   decided inside AppKit classes (`ProfileApps`, `AppOpening`, `Wallpapers`), with no
   tests. Every change to them was checked by hand on the one case being fixed. The
   "Open a new app instance" feature went through five rounds (2026-10-29 02:09, 02:15,
   03:08, 03:18, 2026-11-02 18:09) for this reason. *Now:* `ProfileAppRules` and
   `WallpaperPlan` in DockryCore, 29 tests, one per case the user ran into.
2. **Done was claimed before the real flow was tried.** The weather unit (2026-10-30)
   and the Raycast fix (2026-11-02, first attempt) were reported fixed after checking
   something near the flow, not the flow. The first Raycast fix assumed which app is in
   front before the opened one; macOS reports the order the other way. *Now:* the rule in
   `openspec/config.yaml` stands, and the manual checklist below lists the flows that can
   only be tried on the Mac.
3. **State inferred from the screen and saved for good.** The user's own wallpaper was
   whatever the screens showed at switch time. One screen still showing Coffee's picture
   made Coffee's picture "the user's own" forever. *Now:* Dockry remembers every picture
   it set and never takes one of those for the user's own; old bad entries are dropped.
4. **Profiles are identified by name.** Every store keyed by profile name (app owners,
   window records, fresh app data folders, the active profile) has to follow a rename by
   hand. Three of the first findings (1–3) were this; `ProfileStore.renamed` exists only
   to patch it.
5. **Timing guesses stand in for knowing why something happened.** `switchedAt` (2 s),
   `openingWindow` (3 s), `launcherLeftAt` (1.5 s), hide retries (3 × 300 ms), the
   0.8 s wait for a desktop switch. Each is a guess at macOS's order of events; each is a
   place a fast or slow Mac behaves differently.
6. **Classes do too much.** `ProfileApps` (≈400 lines) owns ownership, persistence,
   hiding, window parking orchestration, sound and activation handling. `AppDelegate`
   wires everything through Combine sinks whose order matters and is only in comments.
   `DockView` (768) and `SettingsWindow` (730) mix layout, state and actions.
7. **Global mutable state.** `Wallpapers` is an enum with static state; `AppWindows`,
   `WeatherMonitor`, `ClaudeUsageMonitor`, `HotKeys` are singletons. Nothing can be
   replaced with a fake, so nothing above them can be tested.

New from this review:

- **Sound in window mode with windows in two profiles** marks both: Core Audio says which
  process plays, not which window. Can't be told apart without per-tab knowledge.
- **A user's own picture that is also a profile's** is never learned as their own (it's
  one Dockry set); that screen falls back to another screen's picture.
- **Display ids change** when a screen moves to another port, which loses that screen's
  own picture (it falls back as above).
- **`DockView.dropGap` writes to `pointer` during `body`**: state changed during a view
  update; SwiftUI may warn or skip updates while dragging files over the dock.
- **Any menu-bar app counts as a launcher**: an app ⌘Tabbed to within 1.5 s of closing
  another menu-bar app's window gets a new window instead of switching profiles.

## What to change, in order

Each step leaves the app working and adds tests before it moves code.

1. **Done (`profile-workspaces`):** `ProfileWindowRecords` and `ProfileAppRules` in
   DockryCore, one mode, no hidden apps, no launcher detection, wallpapers without memory.
   Covers most of steps 3, 5 and 6 below.
2. **Stable profile ids.** Give `Profile` an `id` (UUID, generated when missing, so old
   files load) and key owners, window records, app data and the active profile by it.
   `ProfileStore.renamed` and every rename handler go away. Spec: `profiles-file`.
3. **Split `ProfileApps`** along what it does, each behind a small protocol so the
   coordinator can run against fakes: `AppOwnership` store (persistence, exists in Core),
   `AppHider` (hide/unhide, only what Dockry hid), `ProfileWindows` (already separate),
   `SoundMonitor`, and a coordinator that only applies `ProfileAppRules`.
4. **An app-level test target.** Move the app's code into a `DockryApp` library with a
   thin executable, so the coordinator and the wallpaper apply step get tests with fake
   system services (`NSWorkspace`, AX) injected.
5. **One place that knows why an app came forward.** An `ActivationSource` (dock click,
   Dockry's own window, launcher, ⌘Tab or other) decided once from the event order, with
   the event order itself recorded in a unit-tested sequence, instead of timestamps read
   in several classes.
6. **A profile switch coordinator** instead of sinks in `AppDelegate`: one function that
   does the switch's steps in order (apps, windows, wallpaper, desktop, pinned apps), so
   the order is code, not comments.
7. **Split `DockView` and `SettingsWindow`** by section; move `elements` out of `body`.

## Checks that only the Mac can make

The user runs these, not the developer: they're in
`openspec/changes/profile-workspaces/tasks.md` (section 4). After any change to profiles,
apps or wallpapers, add the cases to that list and test the rules in DockryCore first.
Beyond those:

- [ ] Fresh profile on its own desktop: no other profile's apps in its dock
- [ ] Quit Dockry: macOS Dock back
- [ ] First launch after updating from 0.2.0 with windows parked: they come back on screen
